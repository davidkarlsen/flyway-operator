# flyway-operator

**Generated:** 2026-05-09 · **Updated:** 2026-11-07

## Purpose
Kubernetes operator that reconciles a `Migration` CRD (`flyway.davidkarlsen.com/v1alpha1`) by spawning Kubernetes Jobs which run the [Flyway](https://flywaydb.org/) Docker image to apply database migrations. Built with Kubebuilder v4 (`go.kubebuilder.io/v4`) on top of `controller-runtime`. Module path: `github.com/davidkarlsen/flyway-operator`.

- Operator-owned annotations and labels use the `Prefix = "flyway-operator.davidkarlsen.com"` constant from `api/v1alpha1/migration_types.go`; do not hardcode the domain.

- Env-var defaults use `github.com/caitlinelfring/go-env-default`.

### Architecture

#### CRD shape (`api/v1alpha1/migration_types.go`)

A `Migration` carries three required sub-specs plus optional top-level fields:

- `Database`: `username` + `credentials` (Kubernetes `SecretKeySelector`) + `jdbcUrl` (validated by regex `^jdbc:.*`).
- `FlywayConfiguration`: Flyway-specific knobs (`flywayImage`, which defaults to the operator's `FLYWAY_IMAGE` env var and then to `docker.io/flyway/flyway:13`; `commands`, default `info migrate info`; baseline, default schema, `envVars`, `jdbcProperties`, `volumes`/`volumeMounts`, and `podSecurityContext`/`securityContext` overrides) propagated to the Job.
- `MigrationSource`: an `imageRef` mounted read-only into the Flyway container as an image volume (`volumes[].image`, Kubernetes 1.35+), so the image needs no shell and can be `FROM scratch`; Flyway reads it through `FLYWAY_LOCATIONS=filesystem:/flyway/migration-source/<path>` (user `envVars` can override it). If the API server drops the image volume (ImageVolume gate off), the Job is deleted and the Migration reports `Failed` / `ImageVolumeUnsupported`. Also `path` (default `/sql`, must not contain `..`), `encoding` (default `UTF-8`), `placeholders` and `ImagePullSecret`.
- `retryLimit` (default 2) and `activeDeadline` (default 1h, CEL-validated between 1s and 8760h; becomes the Job's `activeDeadlineSeconds`).
- `jobMetadata` / `podMetadata`: user labels and annotations for the Job and its pod template. CEL rules reject reserved keys (`flyway-operator.davidkarlsen.com/*`, `batch.kubernetes.io/*`, `controller-uid`, `job-name`, `app.kubernetes.io/managed-by`) and invalid label/annotation keys; the operator's own keys always win.
- A CEL rule limits `metadata.name` to 63 characters (it is the Job name and a pod label value).

Status is tracked through `metav1.Condition`s (`Applied`, `Progressing`, `Failed`, all set together with one reason) on `MigrationStatus.Conditions`, plus `observedGeneration`, `attempts`, `lastAppliedImageRef` and `lastAppliedGeneration` (the source image and generation of the last succeeded Job). Reasons: `JobCreated`, `JobRunning`, `JobSucceeded`, `Retrying`, `RetryLimitExceeded`, `TimedOut`, `PreviousJobRunning`, `PreviousJobReplaced`, `ImageVolumeUnsupported`. Helper methods `GetConditions` / `SetConditions` satisfy the `redhat-cop/operator-utils` `ReconcilerBase` interface.

Operator-owned keys, namespaced under `Prefix = "flyway-operator.davidkarlsen.com"`:
- Annotation `<Prefix>/generation`: written onto the spawned Job to track which `Migration.Generation` produced it (`GenerationAsString()`).
- Annotation `<Prefix>/attempt`: the attempt number of the Job (1 when absent).
- Annotation `<Prefix>/paused`: when `"true"` on a `Migration`, `IsPaused()` returns true and reconciliation is short-circuited.
- Label `<Prefix>/migration` and `app.kubernetes.io/managed-by: flyway-operator` on the Job and its pod template.

#### Reconcile loop (`internal/controller/migration_controller.go`)

`MigrationReconciler.Reconcile` (single entry point) does roughly:

1. Fetch the `Migration`; honour `IsPaused()` early-exit.
2. Look up an existing owned Job by deterministic name (`getExistingJob`; the Job is named after the Migration).
3. If the Job exists and its `generation` annotation matches the current `Migration.Generation`, mirror its result into the `Applied`/`Progressing`/`Failed` conditions (with `observedGeneration`). A failed Job is deleted and re-created (attempt +1) until `spec.retryLimit` is exhausted, then the Migration stops with `Failed=True` (`RetryLimitExceeded`, or `TimedOut` when the Job hit its deadline). The status is computed also while a Job is terminating, so `Retrying` / `PreviousJobReplaced` survive a lost status write. A Job of an older generation is waited for while running (`PreviousJobRunning`), otherwise deleted (`PreviousJobReplaced`), recording `lastAppliedImageRef` first if it succeeded.
4. Otherwise build a fresh Job spec via `internal/controller/jobutil.go` (SQL image mounted as an image volume; Flyway container runs with env vars derived from `FlywayConfiguration` and `Database`), apply the restricted security context and submit it (`submitMigrationJob`), with the Migration set as controller owner reference so deletion cascades.

The reconciler embeds `util.ReconcilerBase` from `redhat-cop/operator-utils` and uses its condition / event helpers. Events go to a `record.EventRecorder` (real one in `cmd/main.go`, `record.FakeRecorder` in tests). At startup `cmd/main.go` detects OpenShift (`IsOpenShift`, via the `security.openshift.io` API) and passes it to the reconciler.

#### Metrics (`internal/controller/metrics.go`, `docs/metrics.md`)

`/metrics` is served on `:8443` over HTTPS with controller-runtime authn/authz. Counters and last-run-duration gauges (`flyway_operator_migration_runs_total`, `..._last_run_duration_seconds`) are recorded by the reconciler once per finished attempt; `MigrationCollector` reports condition, transition-time and paused series at scrape time and only after leader election (`mgr.Elected()`).

#### Scheme registration (`api/v1alpha1/groupversion_info.go`)

Uses the upstream `k8s.io/apimachinery/pkg/runtime.SchemeBuilder` pattern, **not** the deprecated `sigs.k8s.io/controller-runtime/pkg/scheme.Builder`. Types are registered inside `addKnownTypes`, not via an `init()` in `migration_types.go`. The exported package symbol for the GroupVersion is `flywayv1alpha1.GroupVersion`; there is no `SchemeBuilder.GroupVersion` field on the new builder type.

### Release and CI

GitHub Actions in `.github/workflows/`:
- `build.yaml`: a `changes` job decides whether code changed; `build` (generated-files check, `golangci-lint` with `--timeout=10m --build-tags e2e`, `make test`, Codecov, multi-arch image, OLM bundle), `e2e` (`make test-e2e` on kind), `govulncheck`, and `ci-success` (the single required check). A `v*` tag additionally runs `release`: builds and pushes the OLM catalog (the catalog image is also tagged `:alpha` for the highest release tag; OLM channels come from `catalog-template.yaml`: `stable-v0` follows every 0.x release, `stable-v0.<minor>` pins one minor), signs the images with cosign, attests operator, bundle, catalog and release assets, and creates the GitHub release. Nothing is committed back to `main`; `catalog-template.yaml` lists releases up to the last committed entry and later tags are added in the workspace only. Verification steps are in `docs/verifying.md`.
- `chart-release.yaml`: publishes the Helm chart (chart-releaser, `gh-pages`, then signing and provenance) on pushes to `main` that touch `config/helm-chart/**` and on `chart-*` tags. The chart is therefore released in a separate PR after the tag build, not by the tag build.
- `chart-test.yaml`: Helm chart-testing (`ct`) using `ct-config.yaml` and `kind-config.yaml`.
- `codeql.yaml` and `scorecard.yaml`: CodeQL and OpenSSF Scorecard scans.

Dependabot opens dep-bump PRs (k8s.io and sigs.k8s.io updates are grouped); when a controller-runtime / k8s.io bump introduces lint regressions (e.g. `SA1019` deprecation), fix the deprecation in the same or a replacement PR rather than pinning the lint rule.
